# Design

## Context

Зачем фича — см. `proposal.md`, что должно получиться — `specs/keep-in-touch/spec.md`, как выглядят экраны — раздел «Макеты» в конце.

Что есть сейчас:

- Таблица `contacts` (имя, «кто это», «откуда знакомы», телефон, почта, `created_at`) и таблица `notes` (`contact_id`, `body`, `created_at`) с индексом по `contact_id`. Заметки можно только добавлять: удалить или изменить заметку нельзя, дату заметки задать нельзя — это всегда момент сохранения.
- Все запросы к базе — в `src/lib/contacts.ts`, только на сервере. Изменения идут через серверные действия (server actions — функции на сервере, которые вызывает форма) в `src/app/actions.ts`.
- В `next.config.ts` включены Cache Components: страницы по умолчанию динамические, а текущее время в серверном компоненте нельзя брать через `new Date()` без явной отметки, что страница динамическая.
- Часовой пояс нигде не задан. Образ `node:24-alpine` и `postgres:18` работают в UTC, поэтому `formatDateTime` на сервере показывает время заметок по UTC. На компьютере разработчика Node берёт пояс Windows, а Postgres в Docker — UTC.
- Автотестов и библиотеки для них в проекте нет. Проверка — `pnpm lint`, `pnpm build` и руками в браузере на тестовых данных из `pnpm db:seed`.

## Goals / Non-Goals

**Goals:**

- Один источник правды для сроков: срок, просрочка и «сегодня» считаются в одном месте — в запросе к базе, по московскому времени.
- Миграция только добавляет: существующие строки не переписываются, предыдущий образ приложения работает с новой базой.
- Блок «Пора связаться» не замедляет главную при 1000 контактов из тестовых данных.

**Non-Goals:**

- История отметок «Связался»: хранится только последняя, так решил владелец. Отдельной таблицы «касаний» нет.
- Часовой пояс на выбор пользователя: Москва зашита в код одной константой.
- Автотесты: для них нужна новая библиотека, это отдельное решение владельца.

## Decisions

### 1. Три поля в `contacts`

- `keep_in_touch_frequency` — частота. Тип базы — перечисление (enum) `keep_in_touch_frequency` со значениями `week`, `month`, `quarter`, `year`. Пусто (`null`) — «Не задано».
- `keep_in_touch_set_at` (`timestamp with time zone`) — когда частоту выбрали последний раз. Нужно для контактов, с которыми общения ещё не было: срок считается от этого момента.
- `last_contacted_at` (`timestamp with time zone`) — последняя отметка «Связался». Пусто — отметок не было.
- Проверка в базе (check constraint): `keep_in_touch_frequency` и `keep_in_touch_set_at` оба пустые или оба заполнены. `last_contacted_at` в проверку не входит: отметка — это факт общения, она остаётся, даже если частоту убрали.

Почему enum, а не `text`: Drizzle выводит из него тип TypeScript, и база сама не пустит опечатку. Добавить значение в enum потом легко (`ALTER TYPE ... ADD VALUE`), убрать — трудно, но убирать варианты не планируется.

Почему не отдельная таблица настроек: у контакта одна частота, связь «один к одному» в отдельной таблице только усложнит запросы.

### 2. Последняя заметка считается, последняя отметка хранится

Последнее общение — самое позднее из двух: последней заметки и последней отметки «Связался». В SQL — `greatest(последняя заметка, last_contacted_at)`: `greatest` в Postgres пропускает пустые значения.

- Последняя заметка — `max(notes.created_at)` по контакту. Считается в запросе через подзапрос с группировкой; используется существующий индекс `notes_contact_id_idx`.
- Последняя отметка хранится в `last_contacted_at`: другого источника у неё нет.

Альтернатива — поле `last_note_at` в `contacts`, которое обновляется при каждой заметке. Отклонена: два места, которые нужно держать в согласии, а при сотнях и тысячах заметок подсчёт на лету занимает миллисекунды. Если когда-нибудь станет медленно — добавить составной индекс `(contact_id, created_at)`, а не новое поле.

Альтернатива для кнопки «Связался» — сохранять заметку с готовым текстом. Отклонена владельцем: заметки — это то, о чём говорили, однотипные записи их засоряют.

### 3. Сроки считает база, по московскому времени

В `src/lib/contacts.ts` — общие SQL-выражения для обоих запросов (карточка и блок):

- начало отсчёта: `coalesce(greatest(последняя заметка, last_contacted_at), keep_in_touch_set_at)`, переведённое в московскую дату: `(... at time zone 'Europe/Moscow')::date`;
- следующий срок: `(начало + интервал)::date`, где интервал по частоте: `7 days`, `1 month`, `3 months`, `1 year`. Postgres сам сдвигает 31 января + месяц на 28 (29) февраля;
- сегодня: `(now() at time zone 'Europe/Moscow')::date`;
- просрочка в днях: `сегодня - срок` (разность дат — целое число). Контакт в блоке, когда просрочка ≥ 0.

Часовой пояс — константа `APP_TIME_ZONE = "Europe/Moscow"` в одном модуле (`src/lib/time-zone.ts`); в SQL передаётся параметром. Запрос возвращает срок строкой `YYYY-MM-DD`, просрочку числом и текущий год — так серверу не нужен `new Date()`, и Cache Components не мешают.

Почему в базе, а не в JavaScript: сортировка и отбор для блока делаются там же, где считается срок, и одна точка отсчёта «сейчас» на весь запрос. Альтернатива — выбрать все контакты с частотой и считать в Node — отклонена: та же логика дат в двух местах, и пояс Node на компьютере разработчика отличается от сервера.

### 4. Время заметок — тоже по Москве

`formatDateTime` и новый формат даты срока в `src/lib/format.ts` получают `timeZone: APP_TIME_ZONE`. Тогда дата заметки в карточке и начало срока всегда совпадают, где бы ни работал сервер. Подписи:

- `formatDueDate("2026-11-28", 2026)` → «28 ноября», для другого года → «28 января 2027». Строка даты разбирается как дата без времени, без сдвига по поясу;
- «просрочено на 1 день / 3 дня / 12 дней» — через существующий `pluralize`.

### 5. Переключатель частоты — Toggle Group из shadcn/ui

Компонент `src/components/keep-in-touch-control.tsx` (клиентский) в карточке, отдельным блоком между контактными данными и «Заметками»: заголовок «Как часто общаться», переключатель, под ним строка о сроке с кнопкой «Связался» справа или сообщение об ошибке.

- Переключатель — `toggle-group` из shadcn/ui (стиль `base-nova`, на `@base-ui/react`), добавляется командой `shadcn add toggle-group`. Новых npm-пакетов он не требует: нужны `@base-ui/react`, `cn` и `class-variance-authority`, они уже стоят. Цвета и отступы — через токены из `globals.css`.
- Пять вариантов видны сразу, выбор — одно нажатие. Альтернатива — выпадающий список (Select): два нажатия и варианты скрыты. На узком телефоне кнопки переносятся на вторую строку.
- Ровно один вариант выбран всегда: нажатие на уже выбранный ничего не делает («Не задано» — отдельная кнопка, а не снятие выбора).
- Пока идёт сохранение, выбранным показывается новый вариант (`useOptimistic`), переключатель недоступен. При ошибке — сообщение «Не удалось сохранить…» в стиле остальных ошибок и возврат к прежнему варианту.
- Кнопка «Связался» видна, когда частота задана, и недоступна, пока сохраняется частота. Как она работает — решение 7.

### 6. Сохранение частоты

- В `src/lib/validation.ts` — `keepInTouchFrequencySchema` (zod enum из тех же четырёх значений) и `null` для «Не задано». Значения для enum базы и для zod берутся из одного списка `KEEP_IN_TOUCH_FREQUENCIES` в `src/db/keep-in-touch.ts`: он лежит отдельно от `src/db/schema.ts`, потому что `validation.ts` попадает и в код для браузера, а `schema.ts` потянул бы туда весь Drizzle.
- В `src/lib/contacts.ts` — `setKeepInTouchFrequency(contactId, frequency)`: если частота та же — ничего не меняет; если другая — записывает частоту и `keep_in_touch_set_at = now()`; если «Не задано» — очищает оба поля. Возвращает `false`, когда контакта нет.
- В `src/app/actions.ts` — `setKeepInTouchFrequencyAction(contactId, frequency)` по образцу `deleteContactAction`: проверка id и значения, ошибка — понятный текст, успех — `revalidatePath("/")` и `revalidatePath("/contacts/[id]")` для этого контакта.
- `addNoteAction` дополнительно вызывает `revalidatePath("/")`, чтобы блок на главной не показывал контакт, которому только что написали заметку.

### 7. Отметка «Связался» и её отмена

- В `src/lib/contacts.ts` — `markContacted(contactId)`: одним запросом записывает `last_contacted_at = now()` и возвращает новое и прежнее значение поля; `undefined`, когда контакта нет.
- Там же — `undoMarkContacted(contactId, markedAt, previous)`: `update contacts set last_contacted_at = previous where id = $1 and last_contacted_at = markedAt`. Условие на `markedAt` не даёт отмене затереть более новую отметку, сделанную в другом браузере.
- В `src/app/actions.ts` — `markContactedAction(contactId)` возвращает `{ markedAt, previous }` строками ISO или понятную ошибку; `undoMarkContactedAction(contactId, markedAt, previous)` проверяет значения через zod и возвращает ошибку, если отменить не удалось. Сами действия страницу не обновляют — это решает тот, кто их вызвал.
- Отметка сохраняется сразу, а не через 5 секунд: так она не теряется, если закрыть страницу раньше. Альтернатива — сохранять, только когда время на отмену вышло, — отклонена по этой причине.
- Время на отмену — константа `UNDO_WINDOW_MS = 5000` в одном месте для карточки и блока.
- В карточке после успешной отметки страница сразу обновляется, и строка о сроке пересчитывается. Вместо кнопки «Связался» на 5 секунд — «Отмечено» и «Отменить». Отмена — `undoMarkContactedAction` и снова обновление страницы.
- В блоке строка 5 секунд остаётся на месте в виде «Отмечено» и «Отменить», затем клиент вызывает `router.refresh()`, и блок приходит с сервера уже без этого контакта. Отмена в эти 5 секунд — `undoMarkContactedAction`, строка возвращается к прежнему виду, обновлять страницу не нужно.
- Ошибка отметки — сообщение «Не удалось сохранить…» в стиле остальных ошибок: в карточке под строкой о сроке, в блоке — в строке вместо частоты и срока. Срок не меняется.

### 8. Блок «Пора связаться» на главной

- Запрос `findContactsToReachOut()` в `src/lib/contacts.ts`: контакты с частотой и просрочкой ≥ 0, порядок — по сроку (раньше — выше), затем по имени и `id`. Возвращает всех: `id`, `name`, частоту, просрочку. Личных контактов с прошедшим сроком немного, а данные компактные — как у общего списка.
- Серверный компонент `src/components/reach-out-section.tsx` в `src/app/page.tsx` — между строкой поиска и списком, в своём `Suspense`. При непустом `q` и при пустом результате ничего не выводит.
- Клиентский компонент со строками: показывает первые 5, кнопка «Показать всех (N)» / «Свернуть» переключает на месте, без запроса к серверу. Альтернатива — параметр в адресе `?reach-out=all` — отклонена: перезагрузка части страницы ради того, что уже пришло в браузер.
- Строки выглядят как строки общего списка (`ContactAvatar`, имя, вторая строка «Раз в месяц · просрочено на 12 дней»). Заголовок «Пора связаться» и число людей — как подпись над общим списком.
- Справа в строке — кнопка «Связался». Она стоит рядом со ссылкой на карточку, а не внутри неё: кнопка внутри ссылки — неправильная разметка, и нажатие открывало бы карточку. У кнопки подпись для экранных дикторов с именем контакта.

### 9. Тестовые данные

`src/db/seed.ts`: примерно трети тестовых контактов — случайная частота, `keep_in_touch_set_at` — дата создания контакта; у части из них — отметка «Связался» позже последней заметки. Плюс несколько контактов в пограничных состояниях, чтобы проверить сценарии руками: последняя заметка ровно 6, 7 и 8 дней назад при «Раз в неделю» (срок завтра, сегодня, просрочено на 1 день), контакт с частотой без заметок, контакт «Раз в неделю» с последней заметкой 20 дней назад и отметкой «Связался» 7 дней назад (срок сегодня — от отметки). Данные по-прежнему одинаковые при каждом запуске, кроме привязки к сегодняшней дате.

## Risks / Trade-offs

- [Время заметок изменится на +3 часа на сайте в интернете] → Это и есть исправление: время станет московским. Сами данные в базе не меняются — в них момент времени с поясом.
- [Просроченных может оказаться много, если сразу задать частоту давним знакомым] → Блок показывает только 5, остальные — по кнопке. Это ожидаемо: с ними действительно давно не общались.
- [Автотестов нет — ошибку в расчёте дат легко пропустить] → Пограничные контакты в тестовых данных и проверка расчёта отдельным SQL-запросом к локальной базе (задача 2.1).
- [Toggle Group на узком телефоне занимает две строки] → Короткие подписи кнопок: «Не задано», «Неделя», «Месяц», «Квартал», «Год» под заголовком «Как часто общаться»; в строке блока частота пишется полностью: «Раз в месяц».
- [Подзапрос по заметкам на главной при каждом открытии] → При 1000 контактов и нескольких тысячах заметок — миллисекунды. Проверяем на тестовых данных: главная открывается так же быстро, как до фичи.
- [Хранится одна отметка: «Отменить» возвращает прежнюю, а после 5 секунд отменить уже нельзя] → Так решил владелец. Ошибочную отметку можно перекрыть только новой заметкой или отметкой позже.
- [«Связался» нажали в двух браузерах подряд] → Отмена в первом ничего не меняет: условие на `markedAt` не даёт затереть более новую отметку.

## Migration Plan

1. `pnpm db:generate --name keep_in_touch` создаёт `drizzle/0001_keep_in_touch.sql`:
   - `CREATE TYPE "public"."keep_in_touch_frequency" AS ENUM('week', 'month', 'quarter', 'year')`;
   - три `ALTER TABLE "contacts" ADD COLUMN` — все без значения по умолчанию, пустые;
   - `ADD CONSTRAINT` — проверка «частота и день её выбора оба пустые или оба заполнены».
2. Что станет с данными: у всех существующих контактов все три поля пустые — «Не задано», отметок «Связался» нет. Ни одна строка не переписывается, заметки не трогаются. Добавление пустых колонок в Postgres не перезаписывает таблицу и проходит мгновенно.
3. Выкатка — обычная: merge в main → образ → на сервере разовый контейнер `migrate` применяет миграцию → стартует новый образ → smoke `/health`.
4. Откат — вручную, запускает владелец: вернуть предыдущий образ. Миграцию откатывать не нужно: старый код перечисляет нужные колонки явно и новых не замечает. Если когда-нибудь понадобится убрать поля совсем — отдельной миграцией, с согласия владельца, потому что это удалит выбранные частоты и отметки.

## Макеты

- Смотреть: https://claude.ai/artifact/9BEbt2CRMG6Ndb4eeNUcEE — холст с экранами для компьютера и телефона, ссылка открывается только у владельца. На экранах главной и карточки можно нажимать кнопки; сегодня в примерах — 28 октября 2026, данные придуманы.
- Исходники — в `mockups/`: по файлу на экран (`Main`, `MainPhone`, `CardDesktop`, `CardPhone`, `States`) и `canvas.json` с раскладкой. Отдельно в браузере они не открываются — им нужен редактор макетов, — но в них видны разметка, тексты, цвета и все состояния, их можно читать при реализации.
- Цвета и шрифты макета — значения токенов из `src/app/globals.css`. В коде брать токены, а не числа из макета.
- В макете три решения по виду, которых нет в требованиях: просрочка выделена красным (`--color-danger`), выбранная частота — синяя рамка со светлой заливкой, у строки о сроке иконка — календарь, когда срок впереди, и будильник, когда пора связаться.
