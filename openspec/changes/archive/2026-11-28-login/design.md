# Design

## Context

Сейчас в `contacts` и `groups` нет владельца. Серверные функции в `src/lib/contacts.ts` и `src/lib/groups.ts` ищут записи по номеру и возвращают общий список. Ими пользуются страницы, серверные действия, а также заголовки вкладок карточек и групп. Заметки связаны с контактами через `notes.contact_id`, а состав групп хранится в `contact_groups`.

Сборка Next.js использует частичную предварительную загрузку. `pnpm test:e2e` поднимает временный PostgreSQL и запускает собранное приложение. На сервере `deploy/deploy.sh` делает резервную копию, запускает миграции отдельным контейнером, затем обновляет приложение и проверяет `/health`.

## Goals / Non-Goals

**Goals**

- Проверять учётную запись и владельца рядом с каждым обращением к данным, включая переходы по старым ссылкам и серверные действия.
- Выдавать письма и проверять ссылки по одним правилам при параллельных запросах и перезапуске приложения.
- Перенести существующие записи целиком и оставить возможность вернуться к паре из прежней версии и её резервной копии.

**Non-Goals**

Границы функции заданы в разделах «Ограничения» и «Не делать» исходных требований. [Пользователи и вход](../../../../specs/02-пользователи-вход.md)

## Decisions

### Вход и защита данных

Better Auth с MagicLink и официальным адаптером Drizzle ведёт пользователей, записи о входе и проверку ссылок в существующем PostgreSQL. Включаем только предусмотренный способ входа. Подключаем форму и переход по ссылке к контролируемым серверным точкам, через которые проходят проверка адреса, лимит и проверка актуальности ссылки. Вызовы Better Auth для выдачи и проверки ссылки остаются внутри сервера. `AppHeader` показывает почту и выход после проверки входа. Настройки внешнего адреса используются для ссылок, а конечная страница и страница ошибки задаются приложением. [Интеграция с Next.js](https://better-auth.com/docs/integrations/next) · [Адаптер Drizzle](https://better-auth.com/docs/adapters/drizzle)

Проверка по одной общей шапке не охватывает отдельные серверные действия и загрузку заголовков страниц. Страницы и действия получают `user.id` из проверенного входа. Запросы к базе требуют этот идентификатор и используют его при чтении и записи. Это касается счётчиков, поиска участников, группы из адреса страницы, заголовков вкладок, «Пора связаться», отметки и отмены. Результаты с данными не попадают в общий кеш между пользователями. `/health` остаётся доступен без входа для проверки выкатки. [Проверки доступа в Next.js](https://nextjs.org/docs/app/guides/authentication#authorization)

Для каждого браузера Better Auth ведёт отдельную запись о входе. Срок в базе и срок cookie, по которой браузер узнаёт свой вход, обновляются на пути реального захода, где сервер может отправить браузеру новую cookie. Проход по ссылке и выход используют обычный механизм cookie Better Auth. Выход отзывает только текущую запись. При проверке сроков учитываем заходы без отправки форм и блокируем обновление просроченной записи. [Сроки входа в Better Auth](https://better-auth.com/docs/concepts/session-management) · [Запись cookie в Next.js](https://better-auth.com/docs/integrations/next)

### Лимит писем и актуальность ссылки

До вызова отправки очищаем и проверяем почту на сервере. Для каждого очищенного адреса PostgreSQL хранит недавние выдачи и отпечаток последней ссылки. Отпечаток позволяет сопоставить ссылку без хранения её исходного значения в дополнительной таблице. Общие правила ограничения запросов Better Auth относятся к точкам входа и не обеспечивают лимит по адресу. Лимит и смену последней ссылки делаем согласованно в базе, чтобы одновременные запросы с разных браузеров не отправили четвёртое письмо и не оставили две действующие ссылки. [Настройки MagicLink](https://better-auth.com/docs/plugins/magic-link#configuration-options)

Резервируем отправку перед передачей письма почтовому серверу. При подтверждённом отказе резерв можно снять, а при неопределённом результате учитываем его до выхода из окна в 10 минут. Запрос сверх лимита оставляет последнюю выданную ссылку действующей. Выдача новой ссылки и приём текущей согласованы в базе для каждого адреса. Срок 15 минут и одноразовую проверку обеспечивает Better Auth, который тоже хранит отпечаток ссылки. Тесты проверяют одновременные запросы и открытие одного письма в двух браузерах. [Одноразовая проверка MagicLink](https://better-auth.com/docs/plugins/magic-link#configuration-options)

### Модель данных и запросы

| Данные | Сейчас | После обновления |
| --- | --- | --- |
| Пользователи и вход | Нет | Таблицы Better Auth и данные для правила выдачи ссылок по адресу |
| `contacts`, `groups` | Общие | Обязательный `owner_id` с привязкой к пользователю. Существующие записи получает владелец CRM |
| `notes` | Связаны с контактом | Принадлежат владельцу через существующую связь `contact_id` |
| `contact_groups` | Связывает контакт с группой | Сохраняет прежние связи. В одной связи обе записи принадлежат одному владельцу |

Проверка владельца через контакт даёт один источник для заметки. Для состава групп используем ограничения базы, которые подтверждают общего владельца в связи, и проверки обеих записей внутри существующих транзакций сохранения контакта и изменения состава. Индексы по владельцу поддерживают личные списки и фильтры. Названия групп могут совпадать у разных пользователей. При создании `owner_id` задаётся на сервере.

Владелец указывает свою почту в `CRM_OWNER_EMAIL` в серверном `.env` перед первым обновлением базы. Контейнер миграций получает переменную из настроек запуска. Локально для миграции и команды создания демо-данных используется та же переменная в локальном `.env`, где можно указать тестовый адрес Mailpit. Значение приводится к тому же виду, что и почта при входе.

### Доставка и сквозные тесты

Один почтовый модуль Nodemailer отправляет сообщения по SMTP, протоколу передачи почты. Настройки запуска подключают Mailpit в локальном Docker и сквозных тестах либо Resend с защищённым соединением на сервере. В Playwright запускаем Mailpit рядом с временной базой и забираем письмо для точного адреса теста через API Mailpit. Существующий сценарий CRM входит под одним адресом в обоих браузерах по разным письмам. Сценарий изоляции использует отдельные адреса и браузерные сессии. [Nodemailer SMTP](https://nodemailer.com/smtp) · [Resend SMTP](https://resend.com/docs/send-with-smtp) · [Mailpit API](https://mailpit.axllent.org/docs/api-v1/)

## Risks / Trade-offs

- Старый процесс может записать строку без владельца между резервной копией и переходом на новую схему. При первой выкатке останавливаем его перед созданием копии и запускаем новую версию после успешной миграции.
- Ошибка в почте передаст старые записи другой учётной записи. Перед выкаткой согласуем источник и сам адрес с владельцем. Если в базе есть старые записи, миграция проверяет корректность адреса и завершается ошибкой при отсутствии нужного значения. Войти как владелец можно только по письму на согласованный адрес.
- Ссылка даёт доступ к учётной записи. Проверяем, что приложение и журнал запросов CRM записывают события без исходных кодов входа и секретов. Учитываем это и в настройках собственного маршрута nginx при выкатке.
- Для настоящих писем Resend требует подтверждённый домен отправителя и ключ. Владелец добавляет DNS-записи и задаёт секреты в `.env` на сервере. Образ собирается в CI, а настройки подхватываются при запуске. [Настройка домена Resend](https://resend.com/docs/dashboard/domains/introduction)

## Migration Plan

1. До вливания показать владельцу миграцию, включая то, какие строки изменятся и как проверить результат. Прогнать её на тестовой базе с данными до обновления. Отдельно проверить чистую базу и повторный запуск. Сценарий старой миграции групп в `contact-groups` начинается с базы без групп. Для перехода на вход проверяем и базу, где группы уже есть.
2. На первой выкатке зафиксировать версию установленного приложения, остановить его и создать резервную копию по существующему процессу. Из образа новой версии запустить отдельный контейнер миграций в проекте `prod`.
3. В одной транзакции создать таблицы входа. Если в базе есть контакты или группы, найти или создать учётную запись для согласованной почты и заполнить `owner_id` у этих записей. Затем включить обязательность поля и ограничения связей. Заметки остаются привязаны к прежним номерам контактов. Миграция сверяет числа контактов, заметок и групп до и после. У записей сохраняются номера, данные и связи. Команда демо-данных использует тот же способ определения владельца.
4. После успешной миграции запустить новый образ и проверить `/health` напрямую и через nginx. Открыть CRM, получить настоящее письмо через Resend и сверить прежние данные под почтой владельца. При сбое выкатка останавливается, результат сообщается владельцу.
5. При ручном откате через границу этой версии использовать пару из резервной копии перед выкаткой и соответствующей прежней версии. Владелец выполняет восстановление через `deploy/restore.sh` и смену версии отдельными шагами. Пока оба шага не завершены, CRM закрыта для пользовательских запросов. `restore.sh` продолжает восстанавливать базу без смены версии приложения.
