# Личная CRM

Приложение для контактов людей, которых знаешь лично: кто это, откуда знакомы, телефон и почта, заметки после разговоров.

Что умеет:

- открывает личный список контактов после входа по письму;
- ищет контакт по имени;
- добавляет новый контакт;
- меняет данные контакта: имя, кто это, откуда знакомы, телефон и почту;
- удаляет контакт вместе с его заметками;
- в карточке контакта хранит заметки — о чём поговорили и о чём договорились.

Идея и границы продукта описаны в [specs/01-продуктовая-идея.md](specs/01-продуктовая-идея.md).

## Что должно быть установлено

- [Docker Desktop](https://www.docker.com/products/docker-desktop/) — в нём работает база данных;
- [Node.js](https://nodejs.org/) версии 20.12 или новее;
- [pnpm](https://pnpm.io/installation);

[OpenSpec](https://openspec.dev/docs/installation) нужен для работы над требованиями фич. В PowerShell его можно установить через `npm install -g @fission-ai/openspec@latest`. Для этой установки нужна Node.js версии 22.20.0 или новее.

Проект уже подключён к Codex и Claude Code. После первого открытия проекта перезапустите редактор, если навыки OpenSpec ещё не видны.

| Выполнить согласованный план         | `$openspec-apply-change`   | `/openspec-apply-change`   |
| Перенести завершённую работу в архив | `$openspec-archive-change` | `/openspec-archive-change` |

В приложении Codex выберите навык OpenSpec в боковой панели. Требования и планы пишутся на русском по правилам в [openspec/config.yaml](openspec/config.yaml). Действующие требования хранятся в [openspec/specs/](openspec/specs/).

## Первый запуск

Все команды выполняются в терминале, в папке проекта.

1. Создайте файл `.env` рядом с `.env.example`: скопируйте `.env.example` и впишите значения. Пароль придумайте сами — он нужен только для локальной базы.
2. Запустите базу данных и Mailpit, локальный ящик для писем:

   ```
   docker compose up -d
   ```

   В локальном `.env` задайте `CRM_APP_URL=http://127.0.0.1:3000` и `CRM_MAIL_TRANSPORT=mailpit`. Для `BETTER_AUTH_SECRET` создайте случайное значение командой `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"` и скопируйте его в свой `.env`. Входите в CRM по адресу из `CRM_APP_URL`. Письма доступны в Mailpit на <http://127.0.0.1:8025>. Порт отправки писем по умолчанию — `1025`. Если укажете другой в `CRM_MAILPIT_SMTP_PORT`, Docker и приложение используют это значение.

3. Установите зависимости:

   ```
   pnpm install
   ```

4. Создайте таблицы в базе:

   ```
   pnpm db:migrate
   ```

5. По желанию наполните базу тестовыми данными. В своём локальном `.env` укажите тестовый адрес в `CRM_OWNER_EMAIL`. Команда создаст для этого адреса 1000 выдуманных контактов с заметками. У трети контактов задана частота общения, у части есть отметка «Связался». По фамилии Тестов можно найти контакты для проверки сроков.

   ```
   pnpm db:seed
   ```

6. Соберите и запустите приложение:

   ```
   pnpm build
   pnpm start
   ```

7. Откройте в браузере <http://127.0.0.1:3000>.

## Обычный запуск

Когда всё уже настроено, достаточно двух команд:

```
docker compose up -d
pnpm start
```

Приложение работает, пока открыт терминал с `pnpm start`. Остановить его можно через `Ctrl + C`, а базу и Mailpit через `docker compose stop`.

## Как проверить, что всё работает

1. Откройте <http://127.0.0.1:3000>, введите почту и нажмите «Получить ссылку». Откройте письмо в <http://127.0.0.1:8025> и нажмите «Войти». С адресом из `CRM_OWNER_EMAIL` видны демо-данные, если вы их создавали.
2. Нажмите «Добавить контакт», впишите имя и сохраните — список откроется на новом контакте, он подсвечен.
3. Впишите имя в поле «Найти по имени», откройте карточку и скопируйте её адрес. Напишите заметку и нажмите «Сохранить заметку». Заметка появится в карточке.
4. В карточке нажмите «Изменить», поправьте, например, телефон и нажмите «Сохранить изменения» — карточка откроется с новыми данными.
5. В карточке другого контакта нажмите корзину рядом с «Изменить», затем «Удалить» — откроется список, этого контакта в нём больше нет.
6. В другом браузере запросите новое письмо на тот же адрес. После входа видны те же данные.
7. Войдите с другой почтой в отдельном окне. Убедитесь, что первого контакта нет в списке и поиске, а по прямой ссылке на его карточку видно «Контакт не найден».

## Автоматические тесты

Запустите Docker Desktop и выполните `pnpm test`. Команда запустит все тесты Vitest, сама поднимет временную базу PostgreSQL в Docker и удалит контейнер после прогона. Если хотя бы один тест пропущен, команда завершится с ошибкой.

Для проверки в браузере после установки зависимостей один раз загрузите браузеры для Playwright:

```
pnpm exec playwright install chromium firefox
```

Запустите `pnpm test:e2e`. Команда поднимет временные PostgreSQL и Mailpit в Docker. Приложение на порту 3100 проверяет вход, изоляцию пользователей и прежние сценарии CRM, в том числе просмотр сохранённой заметки в Firefox. На порту 3101 запускается экземпляр с отдельной базой демо-данных.

## Где лежат данные

Контакты и заметки хранятся в базе PostgreSQL, которая работает в Docker. Данные лежат в томе Docker и переживают перезапуск компьютера и контейнера.

Осторожно с двумя командами — они удаляют данные без возможности вернуть:

- `docker compose down -v` — удаляет базу целиком;
- `pnpm db:seed --reset` — заменяет контакты и заметки учётной записи из `CRM_OWNER_EMAIL` тестовыми. Состав её групп теряет удалённые контакты. Данные других пользователей сохраняются.

Обычная `pnpm db:seed` остановится, если у владельца уже есть контакты.

## Выкатка на сервер

Приложение работает на <https://app.kropcrm.ru>. Новая версия выкатывается сама, когда изменения попадают в ветку `main` на GitHub.

### Перед первой выкаткой входа

1. В Resend добавьте домен отправителя `mail.crm.kropcrm.ru`. В панели управления доменом добавьте записи DNS, которые покажет Resend, и дождитесь статуса **Verified**. Оставьте отслеживание переходов выключенным. [Проверка домена в Resend](https://resend.com/docs/dashboard/domains/introduction)
2. Создайте ключ Resend с правом отправлять письма с этого домена. Сами добавьте в серверный `/srv/personal-crm/.env` строки `RESEND_API_KEY=` с этим ключом, `BETTER_AUTH_SECRET=` с отдельным случайным значением и `CRM_OWNER_EMAIL=` с почтой, которой должны достаться прежние контакты, заметки и группы. Для случайного значения используйте команду из раздела «Первый запуск». Сверьте адрес перед выкаткой. У файла `.env` должны остаться права `600`. [Настройка SMTP в Resend](https://resend.com/docs/send-with-smtp)
3. Из рабочей ветки скопируйте на сервер `deploy/nginx/app.kropcrm.ru.conf` и установите её **только для** `app.kropcrm.ru`, как указано в начале этого файла. Это можно сделать до вливания. Конфигурация отключает журнал ошибок для маршрута входа по ссылке. Записи об ответах на этот маршрут остаются в журнале запросов без кода из письма.

### Как выкатить новую версию

1. Откройте PR в `main` на GitHub и включите автовлитие (**Enable auto-merge**). Для слияния должна пройти проверка **PR checks**. В ней запускаются линтер, проверка формата и типов, Vitest, Playwright с PostgreSQL в Docker и сборка образа приложения.
2. На GitHub откройте вкладку **Actions** — там идёт выкатка «Deploy». Она занимает несколько минут.
3. Зелёная галочка — новая версия на сервере. Красный крестик — выкатка не удалась; GitHub пришлёт письмо.

Что происходит по шагам:

1. GitHub собирает образ приложения и кладёт его в GHCR (хранилище образов GitHub). Имя образа — SHA коммита, например `ghcr.io/kropush/personal-crm:3dcdde3…`.
2. GitHub заходит на сервер по ключу деплоя, копирует туда папку `deploy` и запускает `deploy/deploy.sh`.
3. На сервере скрипт скачивает образ и дожидается запуска PostgreSQL. При первом переходе на вход скрипт останавливает старую версию перед копированием базы.
4. Скрипт сохраняет бэкап в `/srv/personal-crm/backups` и применяет миграции разовым контейнером из скачанного образа. Имя копии содержит префикс `pre-deploy-`, SHA установленной версии, время по UTC и уникальный суффикс. Для первой установки вместо SHA указан `initial`. При ошибке копирования или миграции запуск новой версии отменяется.
5. Запускается новая версия приложения. Пока она стартует, сайт несколько секунд недоступен.
6. Проверка: `/health` должен ответить `200` — и напрямую, и через nginx. Не ответил — выкатка красная.
7. На сервере остаются только образы текущей и предыдущей версий, старые удаляются.

### Как проверить

- Откройте <https://app.kropcrm.ru>, запросите письмо на почту владельца и войдите по ссылке. Проверьте отправителя «Личная CRM», прежние контакты, заметки, группы и настройки общения.
- Откройте <https://app.kropcrm.ru/health> — видно `{"status":"ok"}`.
- В **Actions** на GitHub последняя выкатка — с зелёной галочкой.
- До выкатки подключитесь к серверу через `ssh crm` и запишите версию из `docker inspect --format '{{.Config.Image}}' prod-app-1`. После выкатки выполните `ls -lh /srv/personal-crm/backups/`. Новый файл должен быть ненулевого размера, а SHA в имени файла должен совпадать с записанной версией. В журнале выкатки строка `Database backup saved` должна идти раньше `Applying migrations`.
- При первой выкатке входа проверьте, что `Stopping the old app before the ownership migration backup` предшествует бэкапу, а после миграции прошли обе проверки `/health`.

### Если выкатка упала

Скрипт ничего не откатывает сам. Что сломалось — видно в **Actions**: откройте красную выкатку, шаг «Deploy to the server».

- Сбой случайный (например, не скачался образ) — нажмите в выкатке **Re-run jobs**.
- Нужно вернуть предыдущую версию — откат вручную:

  ```
  ssh crm
  cat /srv/personal-crm/release-previous
  /srv/personal-crm/deploy/deploy.sh <SHA из предыдущей строки>
  ```

  Откат возвращает код, но не таблицы: если новая версия меняла таблицы базы, старой версии они достанутся уже изменёнными.

### Ручной откат к версии до появления входа

1. Подберите пару из старого образа и копии `pre-deploy-<SHA>-…dump`, созданной непосредственно перед первым переходом. SHA в имени копии должен совпадать с тегом старого образа.
2. Временно закройте внешний доступ только к CRM. В блоке HTTPS для `app.kropcrm.ru` добавьте `allow 127.0.0.1;`, `allow ::1;` и `deny all;`. Проверьте и перечитайте конфигурацию командами `sudo nginx -t && sudo systemctl reload nginx`. Снаружи CRM должна отвечать `403`. Локальная проверка выкатки с сервера продолжит работать.
3. Восстановите выбранную копию через `restore.sh` по инструкции ниже. Скрипт запустит установленный контейнер с привычным для него тегом. Внешний доступ оставьте закрытым.
4. Запустите `/srv/personal-crm/deploy/deploy.sh <старый SHA>`. После успешных проверок `/health` уберите три временные строки из конфигурации CRM, проверьте и перечитайте nginx. Проверьте открытие CRM и соответствие данных выбранной копии.

### Как восстановить базу из бэкапа

Восстановление заменяет содержимое базы данными на момент создания бэкапа. Убедитесь, что выбранная копия подходит к установленной версии приложения, особенно если между версиями менялась структура таблиц.

1. Подключитесь к серверу, посмотрите список копий и укажите путь к нужному файлу.

   ```
   ssh crm
   ls -lh /srv/personal-crm/backups/
   bash /srv/personal-crm/deploy/restore.sh '/srv/personal-crm/backups/ИМЯ-ФАЙЛА.dump'
   ```

2. Сверьте показанные на экране путь к файлу, имя базы и версию приложения. Чтобы продолжить, введите `yes`, для отмены нажмите Enter.
3. Скрипт проверит, что файл читается PostgreSQL, и сохранит страховочную копию текущей базы с префиксом `pre-restore-`. Затем остановит приложение, удалит базу, создаст её заново, загрузит выбранную копию и запустит тот же контейнер приложения. Сообщение `Database restored` означает, что скрипт завершился успешно.
4. Откройте <https://app.kropcrm.ru/health>, затем саму CRM. Проверьте, что видны ожидаемые контакты. Текущий образ можно сверить командой `docker inspect --format '{{.Config.Image}}' prod-app-1`.

Если восстановление остановилось после остановки приложения, посмотрите последнюю строку ошибки. После устранения причины можно снова запустить `restore.sh` и указать исходный файл или страховочную копию из строки `Database backup saved`.

### Что лежит на сервере

- `/srv/personal-crm/.env` — пароль и имя базы. Создаётся один раз руками, читает только владелец. В git его нет, выкатка его не трогает.
- `/srv/personal-crm/deploy` — копия папки `deploy` из репозитория, обновляется при каждой выкатке.
- `/srv/personal-crm/backups` — бэкапы базы в формате PostgreSQL, доступны владельцу. Копии остаются на сервере до ручной очистки.
- `/srv/personal-crm/release-current` и `release-previous` — SHA текущей и предыдущей удачных версий.
- База данных — в томе Docker `prod_postgres-data`. Выкатка её не удаляет.
- Настройки nginx для `app.kropcrm.ru` — `/etc/nginx/sites-available/app.kropcrm.ru.conf`, копия — `deploy/nginx/app.kropcrm.ru.conf`. Выкатка их не меняет; если поменяли файл в репозитории — команды для установки написаны в его начале.
- Журналы nginx для `app.kropcrm.ru` — `/var/log/nginx/app.kropcrm.ru.access.log` и `app.kropcrm.ru.error.log`, хранятся 14 дней. Персональных данных в них нет: адреса страниц записываются без строки поиска, без адреса предыдущей страницы, а в журнал ошибок попадают только критические.

Посмотреть, что запущено, и логи приложения:

```
ssh crm
docker ps
docker logs --tail 100 prod-app-1
sudo tail -n 100 /var/log/nginx/app.kropcrm.ru.access.log
```

## Как устроен проект

- `src/app` — страницы: список контактов, новый контакт, карточка контакта, изменение контакта; `/health` — проверка после выкатки;
- `src/components` — части интерфейса;
- `src/lib` — работа с контактами, проверка введённых данных;
- `src/db` — схема таблиц, подключение к базе, миграции, тестовые данные;
- `drizzle` — миграции базы данных;
- `compose.yaml` — настройки PostgreSQL и Mailpit для запуска на своём компьютере;
- `Dockerfile` — как собирается образ приложения;
- `.github/workflows/deploy.yml` — автовыкатка на GitHub;
- `deploy` — скрипты выкатки и настройки сервера.

Стек: Next.js (App Router), TypeScript, React, Tailwind CSS, shadcn/ui, PostgreSQL, Drizzle, pnpm.
